## Rational batching: independent-oracle bill stops construction

The prototype retains the existing contribution callback/cache and batches
three score accumulators as general normalized rational pairs backed by Python
integers. It materializes exact built-in Fractions at each event boundary and
supports odd denominators. Exact Fraction output types do not make its changed
arithmetic an untouched literal Python Fraction oracle.

The bounded probe passed 178 literal/predecessor/candidate comparisons and 19
added controls. The final binder also rejects destructor and unknown-source drift; its exact final
bytes pass finite normal and optimized replay. The earlier binder and every
declared BCCB micro observation are retained. The micro excludes cold build
and has no complete-performance or source-independent oracle admission.

Under the required literal-oracle contract, a complete candidate must pay for
the untouched literal Fraction path, the unchanged integer path, and the new
rational path with separate mutable state. Historical, same-audit observations
retained inside the official export give 20.534678 wall / 20.523067 CPU seconds
for the literal trace and 11.886980 wall / 11.883083 CPU seconds for the entire
replaceable native trace including cold build. Even granting zero cost to the
new rational kernel, conversions, build and all new checks, that replacement
adds about 8.65 wall / 8.64 CPU seconds in this historical screen.

This defeats credible headroom for this exact restoration design. It is a
source-pinned engineering stop, not a fresh complete benchmark, universal
runtime lower bound, or impossibility result. No new actual-word or complete
rational run was performed. The source-qualified packet interface does not
promise arbitrary callback observational equivalence or allocator-level OOM
partial-state equivalence. See [the detailed report](evidence/astra-rational-design.md)
for the complete added validation bill and unresolved construction obligations.
