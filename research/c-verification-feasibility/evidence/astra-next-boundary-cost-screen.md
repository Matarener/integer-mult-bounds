# One bounded reassessment: owned integer state and Fraction ideal control

**Decision before the optional diagnostic: do not construct another route.**
The existing evidence does not establish enough headroom for a further 15%
complete PR5864 wall/CPU reduction. A per-invocation owned integer state is a
materially different boundary and merits, at most, one generous call-boundary
rejection screen. The proposed Fraction ideal loop-control variant is not
currently funded. Neither can borrow the stopped rational-arithmetic or thin
score-wrapper results as a qualified gain.

This worker performed static source inspection only and wrote this report plus
`integer-owned-screen/diagnostic.py` at the parent's explicit further request.
No compiler, Python import, arithmetic/test/timing run, network/browser, Git
mutation or additional agent was used. The diagnostic source has not been
executed by this worker. Parent owns the single guarded runner and decides
whether remaining initial/shared budget funds its one execution.

## Evidence that constrains the decision

The first integer/format nomination preserved its recorded scientific outputs
but failed both the requested 15% threshold and the declared repeat-spread
noise gates. Its descriptive six-process median differences are not an admitted
increment and may not be credited as money already available to a new design.
The fixed comparison remains unchanged and will not be rerolled.

The original complete instrumented profile records individual integer method
cumulative costs of 8.431 seconds (`error_trace`), 3.187 seconds (`reverse_all`)
and 2.622 seconds (`ideal`). It records Fraction `ideal` at 12.508 cumulative
seconds but only 0.756 self seconds, and its `add` helper at 4.422 cumulative /
1.003 self seconds. These are diagnostic observations, not unprofiled costs.
Do not sum the nested helper totals, scale the profile by the 33-second median,
or treat Fraction arithmetic retained inside `ideal` as removable loop cost.

The first C candidate removed large Python sparse loops but added validation,

## Candidate A: exact boundary for private owned integer state

The only candidate boundary retained for screening is the ORIGINAL integer
module at source SHA256
`82a73e4bcf1835bfdd510c7ad5538625c1b380c559b671e6a67be490615a743a`,
specifically `Engine.ideal`, `Engine.error_trace`, and `Engine.reverse_all`.
There would be one private native state per invocation, with no state or answer
reuse across these calls, across repeated words, across backends, or across
processes. The public Engine signatures and complete returned structures would
remain unchanged.

The proposed mechanism is ownership, not another arithmetic wrapper:

- Validate/snapshot a call's allowed immutable operation/weight descriptors
  once. Allocate that call's private rows, columns, score triples and output
  buffers once. Keep original word/setup rejection order and semantics.
- Traverse the program using the existing arbitrary-size Python integer
  primitives and exact division checks. Mutate only privately owned state;
  no external row dictionary can alias an internal row after admission.
- Remove repeated whole-row type scans and `PyDict_Copy` on every sparse
  addition. Avoid returning a score tuple solely to convert it back to a
  Python list at every event. Remove per-event ownership/crossing packets
  where a whole method can run inside the owner.
- Keep full signed coefficient and score byte streams and required witness
  snapshots. Integrate formatting inside the owned traversal; do not count
  the already-tested formatting improvement a second time.
- Materialize the same built-in Fraction boundary values and ordinary output
  containers at the same externally observable method boundaries. Retain
  peak cuts, strict comparison/tie rules, Pareto order, frame/ownership checks,
  all event counts and exact complete hash input.

Original `coefficients`, `setup`, semantic frame helpers, arbitrary-size integer
operations, required Fraction materialization and final hashing/output remain
real work. Even if some of that work moves into C control, it cannot simply be
subtracted from the bill. The screen deliberately includes the entire method
calls, including these retained costs, to give the route the most generous
possible rejection envelope before implementing anything.

The unchanged PR5864 Fraction numerical and bookkeeping route would remain a
fresh independently executed comparison. No new integer state, arithmetic
helper, coefficient result, normalization table or answer cache would enter
that route. New source/code bindings would select the candidate explicitly;
`integer_oracle_unchanged=True` would again be false for an implemented owner.

## Candidate B: C control of Fraction ideal, with unchanged arithmetic

The potential source boundary is `reference_precision.py:49` `ideal()` and,
only where called from that method, its row `add()` loop. It would leave every
actual Python Fraction operation, constructor call, operand, call order and
exception point unchanged. It could move only traversal/dispatch and private
container bookkeeping to C. For example, it must not eliminate the eager
`F(0)` argument in `dst.get(i, F(0))`, bypass `Fraction.__add__` dispatch with a
private `_add` shortcut, cache `abs(q)` calls, or replace the Fraction norm sum
with integer/rational arithmetic. Those would be different nominations.

This is weaker headroom than its 12.508-second cumulative profile suggests:
most of that cumulative region consists of the arithmetic the premise requires
retaining. Built-in iteration, dict operations, sum/map, hashing and string
primitives also already have compiled portions. New C-to-Python arithmetic
calls and source/operation-order checks remain payable. There is no credible
current basis for attributing the approximately five required complete seconds
to removable control overhead in this region.

Under the parent's stated numerical-oracle interpretation, a separately
declared C loop-control implementation could retain unchanged Python Fraction
numerical operations, but its control implementation would still be changed.
It must not be called an unchanged literal Fraction source path. Combining it
with changed integer control cannot silently claim either old control path is
untouched. If the acceptance boundary instead requires the full original
literal Fraction `ideal()` call to remain in the complete qualifier, that call
must execute in addition and its whole cost is paid; the proposed replacement
then does not earn that original call's runtime as a saving.

For this bounded reassessment, Candidate B is deferred without construction.
Do not enlarge Candidate A's eligible bill by adding the whole Fraction ideal
cumulative time. Do not initiate a separate timer/variant search for Candidate B
because the integer screen disappoints.

## Necessary break-even, fixed before the diagnostic

For each metric independently, let:

- B be the already chosen frozen current-round baseline median:
  wall 34.66178539200337 seconds; CPU 34.47 seconds.
- U be the diagnostic's disjoint union of original selected integer Engine
  call intervals across that complete qualifier, including rejected controls
  and finite cases actually touched by the proposed boundary.
- R be runtime retained or introduced inside the replacement boundary.
- A be every added outside-boundary cost: source/runtime/owner checks, cold
  compiler/link/load, extra finite/independence checks and conversions.
- N be the declared noise requirement. This rejection screen uses the frozen
  observed maximum spreads, wall 2.713637237990042 seconds and CPU 2.35 seconds,
  plus the original 0.50-second floor. A later candidate still faces its own
  complete repeat/noise gate; this diagnostic cannot waive it.

The necessary complete saving is

```text
saving = U - R - A
saving >= 0.15 * B
saving > max(0.50 seconds, applicable complete repeat spread)
```

A deliberately optimistic necessary screen sets R=A=0. Since a real
replacement necessarily does some positive work, U must strictly exceed
`max(0.15*B, 0.50, frozen_spread)` in **both** wall and CPU to avoid immediate
engineering rejection. Failure in either metric stops this nomination before
construction. This is a necessary screen, not a sufficient construction gate.
Passing leaves R, A and future repeat noise unpriced and does not authorize
another implementation automatically.

U is a generous observed call-boundary envelope, not a mathematical upper
bound on every machine or future scheduling condition. A one-run rejection is
a predeclared engineering stop for this nomination. It is not a universal
obstruction. This diagnostic is not a replacement performance sample and does
not enter or repair the earlier BCCBBC series.
