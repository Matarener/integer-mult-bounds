# Prime-free native coprime tensor grids

A scoped constructive Word RAM result: deterministically construct odd pairwise-coprime axes in the existing guard-safe bands, including an all-composite option, without primality testing or a Turing-machine simulation. Supply exact CRT input/output streams and a Good–Thomas factorization with the two different address conventions. This is a reference implementation and mathematical proof, not an emitted native instruction trace or a complete multiplication algorithm.

**No larger κ is established.** The donor requested a substantial Word RAM advance. This session does not meet that target. Faster grid setup alone does not improve κ, since the predecessor setup was already subleading. The reusable contribution is a different axis-selection algorithm for a precisely bounded contract; no change to selected-result metadata is proposed.

## Constructive result

Let D = d − 1, with targets t_i in {2^ell, 2^(ell−1)}. For each target choose an odd integer in

    t_i (1 − 1/(3d)) < s_i ≤ t_i (1 − 1/(4d)).

Repeated gcd tests against twice the product of earlier choices select pairwise-coprime axes. Iwaniec's classical Jacobsthal bound guarantees polynomial setup in p = 1 + sum_i log2(t_i), once each selection interval has polynomial length in p. In the usual stretched-exponential axis regime, this holds eventually. The same construction on square roots gives guaranteed composite axes and still succeeds eventually. No explicit finite analytic threshold is claimed; finite requests fail explicitly if an interval is exhausted.

The band satisfies the **complete pinned `production_axis` method**, provided the separate period premise in PROOF.md holds. It does not establish `production_common`, Gaussian approximation, precision, or the rest of the original caller. Actual guard execution is a host semantic adaptation of the pinned source, not execution of the physical tape code.

The two CRT streams use O(N + D) word operations for N = product_i s_i, after polynomial setup, with O(D) metadata. Optional copied coordinate tuples are test-only and cost O(D) each. Materializing or applying the permutation uses O(N) additional data memory. The theorem assumes O(p)-bit native words and explicitly charges setup and memory access.

[#5554](https://github.com/CrocSwap/integer-mult-bounds/pull/5554) analyzes the specific rank-eight productive-helper path and reports essentially exhausted controller-only headroom at the selected local bill; it is not a universal ceiling on other architectures. Its claim was read, not independently replayed here.

The much larger complex-only headline in [#4629](https://github.com/CrocSwap/integer-mult-bounds/pull/4629) is not automatically a complete native multiplication bound. The exact changed charts, controller interface and native assembly must be joined before removing a BIT bottleneck yields that exponent. [#4694](https://github.com/CrocSwap/integer-mult-bounds/pull/4694) and [#4698](https://github.com/CrocSwap/integer-mult-bounds/pull/4698) supply constructive coupled interfaces but explicitly retain unpaid physical-consumer obligations. This package neither repairs nor refutes their large-exponent route.

The existing native Gaussian adapter recount already includes forward chirp convolutions, banded inverse factor reuse and linear address metadata. Rebranding those ideas would not be a new route. Likewise, [#5479](https://github.com/CrocSwap/integer-mult-bounds/pull/5479) supplies a production-scale conditioning result, not a complete native inverse algorithm. These distinctions motivated a new axis-selection experiment, but its successful setup/CRT proof still leaves the dominant transform unchanged. The next budget should go to a complete changed transform or an affordable consumer, not further optimization of this selector.
