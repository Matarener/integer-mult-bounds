# Read the draft catalogue once

Research-draft creation takes 14.55% less median wall time on the measured
default workload after removing one redundant Git process. This is an empirical
tooling improvement with a scoped source-level equivalence argument. It changes
no mathematical bound, supplier or selected frontier.

The contribution was produced by Nick Petalas. New work is Apache-2.0.

## Result and evidence

The old command reads the pinned catalogue through `git show`, then reads it
again in the source-pin batch. The new command reads that catalogue first in
the batch and uses the same bytes for card selection and its source pin. It
sorts the completed inventory into the original order. On Git supporting the
NUL protocol this removes one of the three Git launches. The existing fallback
protocol and source-reader process ownership remain in the shared reader.

| Complete CLI workload | Baseline median, range | Candidate median, range | Median reduction |
| --- | --- | --- | --- |
| Default, two provenance pins | 67.232 ms, 65.786 to 73.393 | 57.447 ms, 56.164 to 61.209 | 14.55% |
| Eight explicit sources, ten pins | 68.880 ms, 66.906 to 90.029 | 59.587 ms, 57.688 to 64.784 | 13.49% |

Each row has 31 measured pairs after one warm-up pair. Pair order alternates
between baseline/candidate and candidate/baseline. Each candidate wins all 31
pairs. All 128 complete commands, including warm-ups, succeed and produce the
same five file bytes and modes within each workload. The measured interval
starts before Python process creation and ends after exit, including Git reads
and all draft writes. Output comparison and moving each draft to scratch happen
after the timer. No source cache or precomputed manifest replaces either run.

[MEASUREMENTS.json](MEASUREMENTS.json) is the generated raw receipt, with each
elapsed sample, output hashes, source hashes, interpreter and platform. The
machine has 18 logical CPUs; load was 3.76 before measurement and the receipt
records the load at completion. Background work was not stopped. Alternating
pair order gives both implementations the same warm filesystem and process-load
conditions. This is one macOS machine, CPython 3.12.15 and Git 2.54.0.

An untimed `cProfile` run of the baseline takes 51 ms inside Python. Generator
creation takes 33 ms; the two ordinary Git calls take 19 ms together, and the
remaining batch path takes 11 ms. Import loading takes 18 ms. The removed
process accounts for about the observed 9.8 ms end-to-end saving. Interpreter
startup/imports and the remaining Git work limit the gain. These profile
durations explain the mechanism; they are not the reported benchmark samples.

## Why generated output is preserved

For a stable checkout and fixed resolved commit, `git show` and the existing
batched blob reader supply the same stored catalogue bytes. Both use the same
sanitized Git source environment. The selected card is unchanged. Every unique
source is still checked against its live file and receives the same blob ID,
SHA256 and usage. Sorting the inventory restores the old JSON order. The code
that renders and publishes the five draft files is unchanged. Therefore every
valid creation has the same generated bytes and file modes in that environment.

`zip(..., strict=True)` exhausts the reader, so a final process-status failure
still prevents publication. Early rejection closes it through the existing
`closing` context. Output aliases and overwrites still reject before Git or
staging writes. Catalogue validation now precedes validation of the other live
files; when several inputs are invalid, the first reported diagnostic can
change. Rejection itself is preserved. Concurrent checkout mutation is outside
the inherited contract.

The direct verifier compares all five files and modes on three additional
baseline/candidate cases, including binary/empty/Unicode sources and duplicated
explicit provenance paths. Nine focused tests cover exact pins, NUL/newline
names, source drift, untracked sources, late reader failure, unknown tasks,
early closure and linked output paths. The retained broader suite covers Git
replacement/root binding, overwrite rejection and the generator/validator
round trip. Locally, all 710 onboarding tests pass with 30 platform-specific
skips. No independent implementation or proof-kernel acceptance is claimed.

## Reproduce

From the repository root, with the local interpreter used for this result:

```sh
/Users/nick/git/integer-mult-bounds/.venv/bin/python3.12 -W error -B research/draft-catalogue-single-read/verify.py
/Users/nick/git/integer-mult-bounds/.venv/bin/python3.12 -B scripts/research_package.py --package research/draft-catalogue-single-read
/Users/nick/git/integer-mult-bounds/.venv/bin/python3.12 -B scripts/check_research_commit.py --package research/draft-catalogue-single-read --check-source-history
```

The manifest runs normal and optimized verification, timed locally at 1.062 s
and 1.147 s. The verifier checks the recorded timing arithmetic and exact
measured source hashes; it does not remeasure performance or certify another
machine's timings. Git and the standard library suffice.

To remeasure, choose a new nonexistent scratch subdirectory outside the checkout:

```sh
/Users/nick/git/integer-mult-bounds/.venv/bin/python3.12 -W error -B research/draft-catalogue-single-read/benchmark.py --scratch /absolute/scratch/draft-benchmark --samples 31
```

The benchmark temporarily creates an exclusively named draft in this worktree
through the real command, then moves it into scratch after each run, including
failure cleanup. The benchmark directory must be on the same filesystem for
these renames. It never overwrites an existing draft or uses the reference
checkout for writes. `baseline.py` retains the exact old generator bytes because
the benchmark executes both implementations; its original notice is unchanged.

## Limits

The measurements cover default and eight-source drafts on one environment.
Windows and older-Git performance were not measured. The shared reader's legacy
protocol is unchanged. Full selected scientific, native, compiler, precision,
BIT, outer-ledger, Lean and Docker replays are unrelated and were not run.
The five selected framework assumptions remain.

Python's managed allocations are retained. The new source loop is bounded by
the finite deduplicated request list and retains one current blob, parsed
catalogue and output inventory. The existing long `create` function largely
contains unchanged templates; a template refactor would expand this scoped
change. The 21-line source-metadata helper isolates the new logic. Dynamic
loading in the verifier is limited to the two declared local generator files.
The benchmark bounds samples to 5 to 101 and each subprocess to 30 seconds.
No optional Python linter or type checker is installed; warning-strict normal
and optimized execution, AST parsing and the repository tests provide diagnostics.

## Open next questions

Does the gain persist for an actual source-heavy package with hundreds of pins?
Start with one named retained source inventory and the same complete command,
including exact output comparison. Materializing those inputs and a separate
measurement budget are the blockers. No further optimization is reserved.
