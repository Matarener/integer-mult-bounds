# Exact invoice experiments for the boundary continuation

This package narrows the next useful native construction. It does **not**
certify a new multiplication supplier or a new κ. It retains the actual
PR3734 controller, helper identities, physical owners and predecessor
assumptions whenever it states an unchanged-contract price.

The source-bound baseline is

\[
0.001730448360207635461740
<\kappa_{\rm PR3734}<
0.001730448360207635461741.
\]

The requested price target is `0.001730578437266246818740`; the retained bit
cap is `0.001733427039589844234749`. The target is slightly above the actual
integer allocation's root. Repeating an entire allocation any integer number
of times scales its child histogram and productive denominator equally and
leaves its moment unchanged.

The exact arithmetic interface and predecessor receipts are in
[`../../kappa-global-continuation/invoice-analysis/`](../../kappa-global-continuation/invoice-analysis/README.md).
Every exponent sign used below is certified with outward rational intervals;
decimal calculations only nominate adjacent 24-digit root endpoints.

## 1. A small genuine fusion would be sufficient

[`screen_tariffs.py`](screen_tariffs.py) and
[`TARIFF-SCREEN.json`](TARIFF-SCREEN.json) retain the complete original
`m=73`, `896`-field-per-replica invoice and price explicit substitutions.
The following are **native implementation targets**, not emitted programs.

| Hypothetical native substitution | Certified root lower endpoint | Clears requested target? |
|---|---:|:---:|
| One pair in the entire 360-replica allocation: `2 H8 -> H16` | 0.001730448648488343393427 | No |
| One pair per replica: `2 H8 -> H16` | 0.001730552147469749147365 | No |
| Two pairs per replica: `4 H8 -> 2 H16` | 0.001730655947182451579889 | Yes |
| One triple per replica: `3 H8 -> H24` | 0.001730695042414312395734 | Yes |

Each upper endpoint is exactly `10^-24` above the displayed lower endpoint.
All these ranks satisfy the retained outer rank guard. A direct sum of two
independent rank-eight children does not itself supply a rank-sixteen native
operation. An actual fusion must identify its single input field, output
contract, admitted route geometry, restored arbitrary helper state and every
additional native charge.

The larger `8 H72` arithmetic screen is outside the inherited guard at
dimension 73: the retained requirement `2 r^2 < m^2` admits at most rank 51.
This is a restriction of the retained recursion, not a theorem about every
possible recursive construction.

## 2. Boundary geometry cannot be treated as free

For the earlier symmetric128-port `m=73` route, the actual retained-owner
allocation leaves room for only `5.98792905023866... H8` at the target.
The price can be optimistically relaxed by putting all 28482 units of paid
idle rank at one maximum rank. Even allowing rank 51 rather than the actual
maximum49 gives only `7.85337789934587... H8`, and rejects eight such
children. This rules out every replica count and packing preserving that
local profile, its256 explicit H1 boundary charge, productive width 1024,
paid idle mass28482 and rank bound51. It does not rule out a changed native
contract or a different boundary construction.

[`partial_tariffs.py`](partial_tariffs.py) independently recounts and prices
all 256 patterns in the sibling
[`PARTIAL-GEOMETRY-CENSUS.json`](../native-boundary/evidence/PARTIAL-GEOMETRY-CENSUS.json).
It extracts the actual idle intervals from the pinned controller and checks
each census histogram. A selected common stage costs224 H1 on the ordinary
ports. A return from a common stage to the original fixed normal costs112
H2, using the two orthogonal normals and the required rank-zero translation.
Every fixed stage also carries the32 H1 zero-port catch-down charge.

All remaining idle rank is again priced at the greatest actual idle rank,
which gives a lower bound on every physical packing's bill. Only the empty
selection, the predecessor `m=73` geometry, passes the target with a free
residual consumer. Every nonempty partial selection fails even before a
consumer is charged. The least expensive nonempty selection is stages
`{7,8}` at `m=75`; its raw deficit is288, but its target allowance is already
negative:

\[
\text{additional H8 allowance}
<-5.1696689673439147300405172195653.
\]

The complete directed intervals are in
[`PARTIAL-TARIFFS.json`](PARTIAL-TARIFFS.json). The mixed cases are conditional
on the stated chart endpoint formulas; they have no emitted full mixed
helper allocation or native residual inverse. The sibling package separately
replays the all-uniform81 endpoint. That endpoint has raw mass82944, exactly
`81*1024`, even granting a free residual inverse and maximal helper-width
credit. Any completed positive child invoice in that family therefore fails
at every positive saving exponent.

## 3. Entry retiming must be priced on its actual owner tails

[`retiming_invoice.py`](retiming_invoice.py) tests each of the408 actual
helper identities under a specific hypothesis: both native providers lose
one H1 per call and the same helper's hosted width decreases by one.
It retains all 1,321,920 helper-owner rows. If the selected identity appears
more than once in a physical idle bin, its full multiplicity enlarges one
remainder; those occurrences are not separately priced as new children.

Under that hypothesis,406 identities strictly improve the actual baseline
and two leave the full profile unchanged. None clears the requested target.
The best identities include native registers293,298,307,309,314,323,325 and330,
each originally of width 4. Their complete profile change is

\[
-6468 H_1+3234 H_2,
\]

and their root lies between
`0.001730565325698224478726` and
`0.001730565325698224478727`. Thus even this favourable one-helper hypothesis
misses the requested target, although it would improve the actual baseline
if a genuine native word established it.

[`RETIMING-SCREEN.json`](RETIMING-SCREEN.json) gives all 408 identities,
provider-specific widths, borrowed-word origin labels, multiplicities,
profile changes and exact target intervals. Historical borrowed helper544
is **native register538**, not native register544.

The single-H1 change is a screening assumption. A real change of entry frame
can split or merge later native climbs and redistribute H2/H3 children.
Its complete local profile must be recounted from the actual native word.
The screen does not authorize replacing that recount with a width total.

The five concrete bare HPE release profiles subsequently supplied by the
entry-retiming search illustrate this distinction.
[`actual_profile_screen.py`](actual_profile_screen.py) and

### Literal allocation fast path for a proved word

[`compact_allocation.py`](compact_allocation.py) accepts two independently
proved NATIVE632-format words. It uses their supplied actual local profiles,
not the single-H1 hypothesis. Its present scope is unchanged data endpoint
spans, helper identities and private zero stock, with positive helper widths
that only decrease and the same eight native centres.

It checks the pinned controller and dispatch, reconstructs all 6480 source
idle windows, checks physical-family interval separation, checks every
source row's strict time eligibility and same-call physical-family
injection, and compacts all offsets using the actual new widths. It then
recounts the full integer invoice and certifies its root. It keeps the
productive denominator322560 and physical-family upper bound323069.

This fast path is prepared for a real native candidate. No changed native
word or allocation is emitted by this package merely to exercise it. Local
operator correctness, including native phases and arbitrary-input
restoration, remains a separate prerequisite.

## 4. What the bounded packing work established

The exact certificate
[`single_swap_barrier.py`](single_swap_barrier.py) directly recounts the
retained allocation and emits
[`SINGLE-SWAP-BARRIER.json`](SINGLE-SWAP-BARRIER.json). Among assigned helpers,
the only positive-remainder width/type pairs are

| Helper width | Bin remainder | Assigned helper rows |
|---:|---:|---:|
| 4 | 1 | 84082 |
| 6 | 1 | 650 |
| 9 | 1 | 252896 |
| 9 | 3 | 116055 |
| 9 | 5 | 14037 |

Including full bins gives11 types. The checker examines all 21 feasible
relaxed type pairs with integer arithmetic. For a swap of widths `wa,wb`,
write `delta=wb-wa`; remainders `(ra,rb)` become
`(ra-delta,rb+delta)`. None of the feasible pairs becomes more unequal.
For fixed sum and `0<p<1`, strict concavity makes `x^p+y^p` decrease exactly
when the two nonnegative terms become more unequal. Consequently **no
single helper-owner swap improves this exact fill**, even if every source
clock and physical-family restriction is dropped.

This is a scoped proof. It does not exclude multi-item changes or a sequence
beginning with a zero-cost swap. The bounded discovery programs
[`local_repack.py`](local_repack.py) and
[`class_repack.py`](class_repack.py) also found no improvement in the tested
same-call exchanges, a two-swap width 6 migration, its eligible cross-call
first-step variant, or620 fixed source-window classes. The retained
`*/SEARCH.json` files are search observations. Their floating-point LP
comparisons are not exact global optimality certificates. No changed FILL
was emitted and no full changed-candidate admission suite was run.

The final bounded experiment examined a longer remainder-token path:
swap width `w` with `w+1` within one call, move the idle unit through full
bins, and finish at another positive-remainder bin. The script
[`augmenting_path.py`](augmenting_path.py) both implements the search and
certifies a stronger source-specific first-step obstruction in
[`augmenting-path/RESULT.json`](augmenting-path/RESULT.json). It covers all
3271 possible initial `(call,width)` contexts and all 8429 first donor rows.
Every starting bin has remainder 1 and width 4 or width 6 as its outgoing
slot. Every possible first donor is full, so the first step merely moves
remainders `(1,0)` to `(0,1)`. After removing its donor, all 21365 untouched
slots across these donor states have the maximum width 9. None can supply a
second unit step to width 10. Therefore a path requiring distinct incoming
and outgoing slots cannot extend past its first step. This excludes the
proposed longer unit-token paths; it does not exclude multi-item changes,
multiple interacting tokens or changed clocks.

## Reproduction

Run from the repository root. `FOLLOWUP` should name the attached, unchanged
followup directory, or its unchanged copy under
`research/kappa-global-continuation/inputs/kappa-consumer-followup`.

```sh
python3 -B research/kappa-boundary-continuation/invoice-experiments/screen_tariffs.py
python3 -B research/kappa-boundary-continuation/invoice-experiments/partial_tariffs.py
python3 -B research/kappa-boundary-continuation/invoice-experiments/single_swap_barrier.py --followup "$FOLLOWUP"
python3 -B research/kappa-boundary-continuation/invoice-experiments/retiming_invoice.py --followup "$FOLLOWUP" --out research/kappa-boundary-continuation/invoice-experiments/RETIMING-SCREEN.json
python3 -B research/kappa-boundary-continuation/invoice-experiments/actual_profile_screen.py
python3 -B research/kappa-boundary-continuation/invoice-experiments/augmenting_path.py --followup "$FOLLOWUP" --out research/kappa-boundary-continuation/invoice-experiments/augmenting-path --seconds 60 --max-depth 32
python3 -B research/kappa-boundary-continuation/invoice-experiments/joint_profile_screen.py --followup "$FOLLOWUP" --cases research/kappa-boundary-continuation/coupled-boundary/combined-subsets/COMBINED-SUBSETS.json --out research/kappa-boundary-continuation/invoice-experiments/JOINT-PROFILE-SCREEN.json
```

All seven certificate commands passed on 2026-10-19. The first three and the
actual-profile screen use the Python standard library. The retiming screen
and token-path/joint-owner censuses use NumPy for integer grouping and the same exact
rational engine for every claimed price. Discovery-only
repacking needs NumPy and, for class LP/MIP search, SciPy.

For an actual independently proved candidate:

```sh
python3 -B research/kappa-boundary-continuation/invoice-experiments/compact_allocation.py --followup "$FOLLOWUP" --base-word "$NATIVE_BASE" --extra-word "$NATIVE_EXTRA" --out "$CANDIDATE_OUT"
```

The last command emits `FILL.json.gz`, `PROFILE.json` and `RESULT.json`. Its
native correctness obligation is stated explicitly in the receipt. It has
not been run on a fabricated candidate.

   dirty-helper contract. Two pair fusions per replica or one triple are
   already numerically sufficient, so this need not wait for a whole
   72-query consumer. The first step is a literal centre/route word with a
   complete native child recount.
2. Produce a genuine additional helper entry retiming, then use its actual
   H1/H2/H3 profile and the retained-owner fast path. A width decrease alone
   is insufficient evidence of a gain.
3. If pursuing unchanged-native packing, begin with a multi-item or changed
   clock construction. Single swaps are now excluded for this fill, and
   exact replication alone cannot help. A promising migration still needs
   literal time eligibility, family injection and integer offsets.
